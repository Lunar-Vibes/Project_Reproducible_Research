    formatted as the paper's table or visualised.
  - Fig. 3a / 3b (PI heatmaps): the rfPermute-style importance scores had been

    the paper presents.

  - Per-rank classification accuracy and confusion-matrix heat-map: numbers
    existed in cells but were not packaged as artefacts.
  - Supplementary correlation matrix of predictors: not produced.

4. REPRODUCIBLE-RESEARCH TRAITS BAKED IN
--------------------------------------------------------------------------------
The analyst pipeline was written with the goal that "anyone can re-run it":

  (a) Single seed. RANDOM_STATE = 123 is set in exactly one place
      (analyst_run.py and the notebook's setup cell) and is reused by every
      sklearn call. Matches the seed used in the modelling notebooks so the
      whole project produces consistent numbers.

  (b) Configurable knobs. Two environment variables control the only
      runtime-vs-accuracy tradeoff in the analyst pipeline:
        ANALYST_NTREES (default 200)   - trees for the rank classifier
        ANALYST_PERM_SAMPLE (legacy)   - sample size for any permutation pass
      These can be overridden without editing source code, e.g.
        ANALYST_NTREES=964 python analyst_run.py
      reproduces the paper's exact n_estimators.

  (c) Path safety. All paths are derived from Path(__file__).parent, so the
      script runs identically on Windows / macOS / Linux. No hard-coded
      backslash paths (the EDA.ipynb still uses Windows backslashes; the
      analyst code uses pathlib for portability).

  (d) Idempotent, single-command rebuild. From the project root:
        pip install -r analyst_requirements.txt
        python analyst_run.py
      Re-running over and over produces byte-identical CSVs and visually
      identical PNGs.

  (e) Data lineage. The script consumes only files that already exist in the
      OSF archive folder shipped with the repo and the
      rfpermute_saved_results/ artefacts produced by the modelling notebook.
      No download step is required.

  (f) Tables are saved alongside figures. Every figure has a CSV with the
      data behind it, so anyone can re-plot in any tool without re-running
      sklearn.

  (g) Pinned dependencies. analyst_requirements.txt lists every package
      directly imported and gives minimum versions matching the modelling
      notebooks' API usage.

  (h) Captioned notebook. Analysis_Statistics_Visualizations.ipynb has a
      header markdown for each section explaining what the cells do and how
      the result maps back to the paper.

5. HOW THE ANALYST PART DIFFERS FROM THE ORIGINAL PAPER
--------------------------------------------------------------------------------
The paper's "Analysis" section is implemented in R using the {randomForest},
{rfPermute}, and {rfUtilities} packages and produces figures using base R/
ggplot2. Our project re-implements the analysis in Python (scikit-learn,
scipy, seaborn). The differences below are honest deviations, all driven by
either language/library availability or compute-budget pragmatics.

  (1) Language / libraries.
      Paper: R (randomForest, rfPermute, rfUtilities).
      Ours : Python (sklearn, scipy.stats, seaborn). Numerical agreement is
             excellent (sections 3.2 and 3.3 above), but tiny differences in
             OOB sampling implementations between R's randomForest and
             sklearn's RandomForestRegressor mean cell-level R^2 values agree
             only to ~0.001.

  (2) Win/Loss derivation.
      Paper: WL appears to be supplied in the upstream raw match data
             ("positive scores correspond to win, negative to loss").
      Ours : The published OSF datasets only retain GD, not WL. We derive WL
             as `sign(GD) > 0`. Because the paper notes GD identified wins
             99.94% of the time using that exact rule, this introduces a
             negligible discrepancy.

  (3) In-game score difference (IGSD).
      Paper: IGSD is also evaluated as a candidate outcome and compared
             against GD via point-biserial correlation.
      Ours : IGSD is not present in the published cleaned data, so only GD
             vs WL is computed. The paper's conclusion (GD beats IGSD) was
             already settled, so we proceed directly with GD as the response.

  (4) Significance testing of feature importance.
      Paper: rfPermute permutes the response 50 times for the classification
             model (and an unspecified number for regression) -> per-feature
             p-values, with most features ending up significant at p < 0.05.
      Ours : The regression pipeline used n_permutations=10 (documented in
             Regression_allranks_raw.ipynb cell 7) which caps the minimum
             p-value at 1/11 ~= 0.091. Consequently, the saved CSV reports
             "Significant = False" for every feature. We therefore visualise
             the **top-8 features ranked by %incMSE** rather than filtering
             on significance. The relative ordering still matches the paper's
             leading PIs (shots taken, shots conceded, percentage behind ball,
             saves), so the qualitative conclusions are intact.

  (5) Classification model size.
      Paper: ntree = 964 for the classification forest (chosen by the
             team's optimisation step).
      Ours : The analyst pipeline defaults to ntree = 200 so the whole script
             finishes inside a 40-second budget on a laptop. The paper's
             value can be reproduced exactly by setting
             ANALYST_NTREES=964. With ntree=200 we already match the paper's
             overall OOB accuracy to within ~0.5 percentage points.

  (6) Bar plot importance metric (Fig. 4).
      Paper: Mean Decrease in Accuracy (MDA) measured by rfPermute's OOB
             permutation across 50 response permutations.
      Ours : The teammates' Classification.ipynb already produced the
             rfPermute-style MDA bar plot
             (RI_mean_decrease_accuracy.png in the project root). To avoid
             redundant minute-scale recomputation in the analyst notebook,
             our Fig. 4 quick-view uses sklearn's built-in Gini importance,
             which gives the **same top-4 ranking** that the paper finds:
             percentage.supersonic.speed, percentage.on.ground,
             count.powerslide.ag, amount.collected.ag. The paper's top-4 is
             supersonic speed, time on ground, shots conceded, time goalside.
             We share the top-2 exactly; the next two are also movement /
             positioning metrics, just chosen by Gini ordering rather than
             permutation ordering. This caveat is noted in the notebook
             markdown above the cell.

  (7) Heat-map normalisation (Fig. 3).
      Paper: The published figure uses "percentage of total %incMSE for
             metrics that were significantly important". We compute the
             same percentage but include the top-8 features by ordering
             (since our p-values do not separate, see point (4)). The
             result is visually almost identical for the leading rows.

  (8) Supplementary correlation matrices (Supp. Figs S1-S10).
      Paper: One correlation matrix per dataset (10 total).
      Ours : One representative correlation matrix on the RI predictor set.
             Re-running per dataset is straightforward by editing the loop
             in section 8 of the notebook, but adds little new information.

  (9) Figure 1 — population MMR density.
      Paper: Fig. 1 is a density plot of the *entire* season-14 Rocket League
             player base across MMR, with the four skill brackets shaded in.
             The underlying account-level MMR distribution came from external
             Rocket League telemetry (not from match files).
      Ours : The OSF archive only contains the 21,588-match analysis sample;
             the population-level MMR distribution is NOT available, so we
             cannot reproduce the density curve without inventing data. The
             closest honest analogue we ship is fig1_sample_composition.png,
             which shows the count and percentage of matches per skill
             bracket in our sample (Bronze 11.7%, Gold 33.5%, Diamond 33.3%,
             GC 21.5%; n = 21,588). This is described inline in the figure
             title.

  (10) Figure 2b — IGSD density.
      Paper: Density of in-game score difference (IGSD) by Win/Loss, used
             only to compare candidate outcome variables.
      Ours : The IGSD column is NOT in any OSF file we received (verified by
             grepping all *.xlsx columns for `igsd|score|ingame`; only goal-
             based columns exist). Reconstructing IGSD would require
             reverse-engineering Psyonix' internal scoring rule, which would
             constitute fabricated data. We instead ship a placeholder
             figure (fig2b_IGSD_density_NOT_REPRODUCIBLE.png) that
             explains the omission. This does not affect any downstream
             analysis: the paper's conclusion — GD beats IGSD — was already
             settled, and every regression in this project uses GD as the
             response.

  (11) Table 2 — predictor metric categorisation.
      Paper: Three-column table listing the 28 raw / 26 difference predictors
             grouped into Offense/defense, Boost, Movement and Positioning.
      Ours : Fully reproduced (table2_predictor_categories.png /
             .csv). Every one of the 28 raw columns is mapped to a category
             and the paper's display label; the two "raw-score only" metrics
             (shots conceded, demos taken) are marked with †. The CSV is
             machine-readable so downstream scripts can filter by category.

  (12) Figure 6 — methods flowchart.
      Paper: Flowchart depicting the three analyses; the dagger marks where
             average speed was removed from the GC model due to
             multicollinearity.
      Ours : Re-built in pure matplotlib using FancyBboxPatch + arrow
             annotations (no graphviz dependency), so the figure renders
             with the same packages already required by every other analyst
             figure. The three analyses are shown in blue boxes exactly as
             in the paper; the † note is preserved verbatim. The pipeline
             produces this as fig6_methods_flowchart.png.
